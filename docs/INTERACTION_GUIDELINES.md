# AI Launcher 交互设计规范与指引

> 版本：v1.0 草案（2026-10-20，待 Bob 过目）
> 来源：西瓜同学《让 AI 做的 App 和小程序更精致的 6 个交互》（抖音，《App 和小程序的高级交互》第 14 集）的方法论 + 本项目已立的交互原则合并而成。
> 定位：这是「怎么做才算精致」的判定标准，不是视觉稿。每个新功能、每次改版先对照本文自检，再动手。

---

## 0. 总纲：精致感来自反馈，不来自装饰

AI 生成的界面"按钮能点、页面能跳"，但用起来总觉得差一点——差的就是**交互反馈**：用户做出动作之后，界面有没有用动画、状态、声音把"我收到了、正在发生、已经完成"讲清楚。

本项目的判定标准一句话：**任何一次用户动作，都必须有可感知的回应；任何一次状态变化，都必须有可见的来路和去向。**

---

## 1. 六个基础反馈模式（视频方法论，通用化）

### 1.1 完成反馈（Done Feedback）
动作完成的那一刻，给一个短促、明确的"成了"信号，而不是无声无息地结束。
- 典型形态：按钮形变（挤压回弹）→ 状态符号出现（打勾）→ 微粒迸发，一共三拍，约 300–500ms 收束。
- 适用：任务完成、发送成功、收藏/添加成功、下载完成。
- 要点：反馈必须**跟在动作后面立刻发生**，延迟超过 100ms 就断了因果感。

### 1.2 状态联动（Linked State）
一次操作，所有受影响的地方**同时**变化，不留"这边变了那边没变"的半成品状态。
- 典型形态：勾选一个任务 → 勾选框打勾 + 进度环增长 + 数字滚动，三处同步。
- 要点：联动的每一处都要有自己的动画（数字滚动、环增长），而不是静态替换——静态替换看起来像 bug，动画看起来像设计。

### 1.3 叠放与展开（Stack & Fan）
内容多时默认叠放收纳，用户召唤时完整展开，收起时整齐归位。
- 典型形态：卡片叠放 → 点击扇形展开、每张完整露出 → 再整齐叠回。
- 要点：展开和收起必须是**同一条动画的正放和倒放**，用户能预判东西从哪来、回哪去。

### 1.4 吸附与描绘（Snap, then Draw）
手势操作分两拍：先让对象**吸附落位**（告诉用户"停在这了"），再让细节**描绘呈现**（告诉用户"接下来是什么"）。
- 典型形态：滑动卡片 → 吸附停靠 → 停稳后时间线一笔画出。
- 要点：顺序不能反。先画线再吸附会显得乱；先落位再展开细节，用户才有掌控感。

### 1.5 物理惯性（Inertia & Snap）
可滚动/可拨动的东西必须带惯性：甩出去会继续走、逐渐减速、最后吸附到最近的刻度。
- 典型形态：滚轮快速拨动 → 惯性滑行 → 减速 → 吸附停靠，停靠瞬间可配一记轻震动。
- 要点：惯性曲线决定"手感高级感"的大头。匀速滑动是廉价感的头号来源。

### 1.6 源点转场（Origin Transition）
页面/面板从用户手指点下的位置生长出来，返回时原路收回。
- 典型形态：点击处圆形扩散铺满全屏；返回时从原点收回。
- 要点：转场锚点 = 触发点。用户永远知道新界面是"从刚才那个东西里出来的"，空间感不断裂。

## 2. 映射到 AI Launcher：现状与差距

| 模式 | 本项目现状 | 差距/机会 |
|---|---|---|
| 完成反馈 | 点七仔果冻+开心表情是达标的完成反馈；盲操松手启动有震动+语音 | TODAY 卡片上的动作（回拨、加入会议等）点完多为直接跳转，缺一拍"已执行"确认；OTA 下载完成、添加装备成功等长流程节点缺完成信号 |
| 状态联动 | 扇形展开时 TODAY/Dock 淡到 0.3 是联动意识的体现 | 操作后多表面同步不足：如标记完成/删除后，计数、徽标、七仔状态不同步动画更新；应做到"一处操作，处处有回应" |
| 叠放与展开 | 盲操扇形本身就是扇形展开的成熟实现（展开/收起同路径） | TODAY 多区块内容目前是平铺长列表，可评估高频区叠放、展开看全量 |
| 吸附与描绘 | 扇形拍照段有边界磁吸 ±10°（吸附已有） | 吸附后缺"第二拍"：落位确认的描绘/点亮动画；房子回首页的绽放已接近此形态，可提炼为通用规范 |
| 物理惯性 | 扇形跟手滑动、快滑直拍（速度阈值）有物理意识 | 字母导航 rail 快速滑动无惯性吸附；未来一切滚轮/选择器类控件必须带惯性+吸附，不许匀速 |
| 源点转场 | 房子"原地绽放"、点七仔反馈都是源点动画 | 进 D3 应用中心、设置页等转场仍是系统默认切换，无源点生长感；转场统一锚定触发点是下一阶段的系统性机会 |

结论：本项目在**手势类**反馈上已经领先（扇形、绽放、磁吸都是这套方法论的实例），短板在**信息类**操作（TODAY 动作、列表操作、长流程节点）的完成反馈与状态联动。

## 3. 本项目专属规范（已立原则，成文固化）

以下为 Bob 已拍板、本项目独有的规则，与第 1 节的通用模式冲突时以本节为准。

### 3.1 反馈三通道分级
一次操作的反馈按重要性选通道，可叠加：
- **视觉**（默认）：形变/位移/透明度动画，必须跟手或紧随动作。
- **触觉**（确认点）：滑入选中、吸附落位、越过阈值时给一记短震动；同一手势内不连震。
- **语音**（七仔）：只用于模式切换、结果播报、技巧提醒；不逐条念普通操作，避免啰嗦。
分级原则：普通操作=视觉；手势关键节点=视觉+触觉；状态/结果变化=视觉+七仔择一播报。

### 3.2 非模态优先
信息展示一律走非模态（七仔气泡+TODAY 卡片+动效）。弹窗仅限：用户主动触发、或安全相关（删除确认、添加流程、隐藏 Dock 确认、低电量提醒）。新功能评审第一问："这个信息能不能不弹窗？"

### 3.3 每条信息配下一步动作
展示信息的同时给出用户最可能的下一步（未接电话→回拨、会议→加入、消息→打开会话）。只展示不给动作的信息视为未完成设计。

### 3.4 手势语义一致性
- 全局签名：左滑（从右往左）= 多/展开，右滑 = 少/收起；Dock、应用行、组头、首页卡片、宠物标签统一。
- 新手势先查冲突表（docs/GESTURES.md），再谈手感；语义反了的手势不许上线。

### 3.5 跟手与意图驱动
能跟手的动画一律跟手（位移/缩放跟随手指），不做"触发后播一段固定动画"。松手即按意图结算：到位执行、不到位复位，不留中间态。

### 3.6 单手可达
高频控件落在单手拇指活动范围内布局；新增常驻控件先标注其拇指热区位置再评审。

### 3.7 引导走七仔说话
操作教学、状态解释由七仔开口，不用静态说明文字堆在界面上。省电前提下只在用户看桌面时刷新与播报，网络请求加缓存节流。

### 3.8 参考的边界
参考 iOS 等标杆只学视觉语言与反馈模式，尺寸/布局必须按本项目内容量重新设计；原型与成品必须用 App 实际主题色，不得臆想配色；IP 角色必须用真实资产。

## 4. 动效参数基线（建议值，评审时可调）

| 参数 | 基线 | 说明 |
|---|---|---|
| 完成反馈总时长 | 300–500ms | 超过 600ms 用户会觉得"慢" |
| 页面/面板转场 | 250–350ms | 源点扩散与内容淡入可并行 |
| 跟手动画 | 0 延迟，1:1 跟随 | 松手后惯性/复位 ≤300ms |
| 缓动曲线 | 减速出场（decelerate）为主 | 入场可轻微回弹（果冻类），但幅度克制 |
| 状态联动数字变化 | 滚动/递增动画 200–400ms | 不许静态跳变 |
| 震动 | 单次 10–20ms 短震 | 仅关键节点，同一手势最多 1 次 |

## 5. 新功能交互自检清单（交付前逐项过）

1. 每个可点元素按下时有即时视觉回应吗？（<100ms）
2. 每个动作完成后有明确"成了"的信号吗？还是无声结束？
3. 一次操作影响的所有表面（计数/徽标/列表/七仔）都同步变了吗？
4. 展开类动画收起时走原路返回吗？
5. 手势有吸附/落位反馈吗？落位后有第二拍呈现吗？
6. 可滚动控件有惯性和末端吸附吗？还是匀速廉价感？
7. 页面转场能看出是从触发点长出来的吗？
8. 有没有本可以非模态却用了弹窗的地方？
9. 每条展示信息都配了下一步动作吗？
10. 新手势与全局签名（左多右少）冲突吗？跟手吗？松手有结算吗？
11. 高频控件在单手拇指热区内吗？
12. 动效时长/震动次数在基线内吗？

## 6. 反模式（明确禁止）

- 点击后无任何变化、直接跳走（无反馈跳转）
- 状态静态跳变（数字/徽标瞬间替换）
- 展开动画有去无回、收起路径与展开不一致
- 匀速滚动/匀速转场（廉价感来源）
- 信息类内容用模态弹窗（违反 3.2）
- 用静态文字做教学引导（违反 3.7）
- 照搬参考产品的尺寸布局（违反 3.8）
- 同一手势内连续多次震动
- 动画未跟手却要求用户"等它播完"
